# Consultation blueprint comparison

Compared on October 22, 2026 against `SmartSehat Consultation Final-Round Blueprint (1).md`, current sources and recorded verification. Includes quick danger capture, experimental regional speech, lossless transfer/recovery, an inactive partner delivery adapter and complete patient-guidance audio. See `consultation_integrations.md` for the latest contracts. The existing Streamlit build is the user's chosen implementation; the React/FastAPI layout in the separate one-week document is not treated as a missing feature.

## Overall finding

The core worker-to-doctor consultation loop is implemented as a local research prototype. The full blueprint is not completely implemented or independently validated. Software gaps remain in addition to external clinical review and deliberately simulated services. The user's requested approximate completion scores are recorded in `blueprint_completion_status.md`: roughly 90% for the core consultation workflow and 80–85% for the broader project scope, excluding deferred presentation assets. These are engineering estimates, not measured accuracy, safety, performance or clinical-readiness percentages.

`Implemented` below means a software feature exists in the current prototype. It does not mean clinical validation, tested performance on a low-end phone or real external delivery. `Partial` identifies a narrower implementation. `Simulated` means the app records/displays the action without carrying it out through a real service.

## Additional software gaps found during this comparison

1. **Cache warm-up mismatch: addressed.** The helper and app now share the schema/question-contract/version-bound key and encrypted writer. Authored English/Roman Urdu extraction fixtures cover every age pathway; all 48 question identities and the fictional image are prepared. Valid existing responses are preserved, including migration of plaintext caches. An explicitly synthetic manifest can add exact-input schema-valid fixtures for supported operations. The executed helper prepared 61 files without provider calls or patient mutations. This is a finite authored fixture set, not comprehensive coverage of arbitrary inputs or model quality.
2. **Repeated-handoff timing: addressed.** Sends, returned tasks and shared worker questions start an audited handoff. Acknowledgements/replies bind that handoff; old actions cannot stop its escalation. Metrics report separate cycle histories and a pending value until the current cycle is answered, keeping simulated clock advances separate from wall-clock timestamps. These event timings do not establish clinical effort saved.
3. **District/month context software addressed; reviewed content pending.** Worker-confirmed country, province, district, reference date, unknown reason and reported exposure notes survive drafts, bilingual read-back and exports. Exact reviewed place/month/date-window matching is available; missing/unreviewed/ambiguous context stays explicit. Catalogue changes invalidate packets and doctor/wording approval, and current context is visible to the doctor. The shipped table remains empty: no actual local disease prior, calibrated probability or invented risk statement is active. See `fever_context_contract.md`.
4. **Availability and failover software: addressed within the simulation.** Roster changes persist with encrypted immutable audit. Unacknowledged cases reassign to an available compatible reviewer without resetting their handoff; the first escalation selects an alternate when one exists. No compatible reviewer stays explicit, and pregnancy/language eligibility is preserved. Per-urgency delay configuration is validated transactionally. Real clinician availability, notifications and approved operational timing remain external inputs.
5. **Selected-product regimen software addressed; clinical rows/full prescription interpretation pending.** The doctor records product, mg per dose, daily count/maximum if needed, course length and indication. Reviewed entries can constrain per-dose/absolute amount, daily maximum, frequency, duration and indication. Missing limits/inputs remain explicit; as-needed selection cannot bypass a daily cap. No dose is supplied or inferred. Combination products, organ function and free-text/multiple-medicine schedule interpretation still require independent doctor verification. Actual clinical rows/approval remain absent. See `dose_entry_contract.md`.

The latest danger-screen closure is recorded in `danger_screen_completion.md`, following `consultation_integrations.md` and `steps_1_to_7_status.md`. The wider review archive contains 38 Urdu and 66 English fixed prompts; 27 wider question phrases remain unprepared. All danger prompt audio is prepared. No actual clinical/native-speaker review, independent field usability or external delivery was fabricated.

## External services, deferred work and final-round scope

Real clinician verification, authentication, facility receipt, transport and live stock remain simulated or absent. A partner messaging gateway adapter is prepared but inactive without credentials. The user confirmed no clinical reviewers or service credentials are currently available. The separate one-week plan allows simulations; actual delivery and clinical validation remain incomplete.

Full regional interfaces/TTS and validated speech, automatic offline sync, provincial/DHIS2 deployment and outcome-linked district reporting remain future work. Manual regional capture/read-back and five opt-in experimental STT routes are present. The blueprint's broader multi-month roadmap is not completed by this build.

Presentation work remains deferred under the user's instruction: existing script/scaffold files are not evidence of a finished slide deck, timed rehearsal or backup video. This comparison does not create those assets.

Before calling the implementation complete against the entire blueprint, resolve the software gaps above, obtain clinical/pharmacist inputs for the relevant features, validate the target phone/languages and explicitly decide which real-service/offline requirements remain outside the prototype. Keep software completion, clinical approval and deployment readiness as separate claims.
